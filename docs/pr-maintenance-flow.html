Copilot Fleet / PR maintenance / workflow draft

Keep the PR moving. Keep design decisions human.

Maintenance continues an existing, eligible coding worker through review and repair rounds. The same Orchestrator coordinates it on its existing wakes; there is no second scheduler or always-on observer agent.

The Host remembers. The helper reads GitHub. The lead decides. The worker repairs. The human controls design.

This explains the implemented control flow, not a proven live-agent outcome. Real-agent maintenance evaluation is still pending.

01

The normal repair loop

The local-repair path is shown here. Every dispatch still needs valid authority, complete evidence, an eligible worker and available budget.

02

Design choices stop the whole PR

The lead classifies the feedback, and the worker must reconsider the boundary when inspecting the code. A small diff is not automatically a local repair.

03

Watching, ready, and finished are different

Unchanged / pending

Wait without busywork

No new actionable input means no repair turn or duplicate reply. Pending checks wait; CI failures can become work even without a new comment.

Ready to merge

Notify, then keep watching

Current feedback, required checks, reviews and mergeability must all permit readiness. Ready is nonterminal. Maintenance never merges the PR.

Merged / closed

Stop admission, then settle

No new repairs. Request cancellation of the bound in-flight work, reconcile accepted pushes and replies, and release ownership only after settlement. Unknown effects keep their reservation.

Fail closed: a busy or offline worker, incomplete snapshot, stale binding, exhausted budget, or uncertain effect means wait, reconcile or seek human attention. Never substitute a new worker or pretend the action succeeded. An explicit pause stays paused.
