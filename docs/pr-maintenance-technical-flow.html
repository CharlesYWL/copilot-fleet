How the PR Maintainer works

Which MCP tools and REST actions start, change and end PR maintenance, and how the registration, batch and displayed stage change. Read directly from the code at commit d3d5311 (2026-09-23).

00

Mental model in five roles

Memory

Host registry

SQLite tables pr_maintenance, _proposals, _wakes, _scans. The lead re-reads it every wake; conversation memory is never authoritative.

Decides

Lead + SKILL.md

Observe → triage → prepare batch → dispatch → settle, or escalate. Never writes code itself.

Reads

snapshot.mjs

Packaged read-only helper; ADO via Node-local az, GitHub via GraphQL. Bounded by the claim.

Repairs

Retained worker

The same coding session and checkout that built the PR, continued with fleet_follow_up.

Authorizes

Signed-in operator

Only REST from a browser session can authorize, resume, renew, release or give design direction. MCP can propose and pause — never approve.

No new scheduler. Maintenance rides on existing lead wakes. nextCheckAt = the first orchestrator heartbeat at least 30 min after the last attempt; an idle lead with due work gets a status-check prompt on that heartbeat schedule (cron, default hourly on weekday working hours, two-hourly otherwise) and claims it with takeDue. A PR whose retained worker is still running an accepted batch is not claimed.

01

Who talks to whom

Operator actions go through REST; the lead's actions go through Fleet MCP tools; both land in the same SQLite registry. The engine turns registry facts into lead wakes and dispatches worker turns.

02

Start: prepare → propose → authorize

Two turns and one human click. The lead can only create an unapproved proposal; the registration exists only after the signed-in operator authorizes that exact proposal version.

03

Every wake: claim a due PR and observe it

The lead claims one due PR per visit, runs the read-only helper bound to that claim, and persists the exact output on the completion wake. The Host, not the model, then decides what changed.

06

How the displayed stage changes

The stage rail is a pure projection — prMaintenanceProgress(record) — recomputed from durable facts after every checkpoint. Overrides are evaluated first in a fixed order; only when none match does the working loop apply. Nobody writes a stage string.

Exact precedence (first match wins)
#StageCondition
1merged / closedlifecycle is merged or closed
2releasedownershipReleasedAt is set
3human_holddecision pending, or paused with task_human_hold
4reconcilingunresolved effects incident; batch uncertain/reconciling; dispatched batch not execution-settled; accepted batch with cancellation requested; any reserved/uncertain effect
5authorization_requiredlegacy grant without publicationAuthorized (and no active manual control)
6paused · blockedlifecycle paused (blocked when reason is authorization_failed or remote_identity_changed)
7blockedlast attempt saw a draft or merge conflict
8recovering · blockedan unresolved incident — capability with < 3 alternate attempts is recovering, anything else blocked
9blockedlast attempt failed / incomplete / differs from the last complete observation
10addressing_reviewa batch is accepted (worker is on it)
11checkingno complete observation, or older than 30 min
12triagesome observed source has no addressed / already_satisfied finding verified at current HEAD
13waiting_checkschecks incomplete, or any check not passed at HEAD
14waiting_reviewreviews incomplete, or any review not approved at HEAD
15readyopen + mergeable + no outstanding batch + readyFingerprint == fingerprint (else checking)

Rounds shown in the UI = executed, settled batches only (distinct step:attempt). Reservations, batches cancelled before dispatch and provider review iterations do not count.

07

Batch lifecycle: a worker's “done” is not settlement

A batch only frees its slot after the Host has a correlated terminal step receipt with a quiescent worker and the lead has checkpointed every finding, effect and the real mutation count.

09

Numbers that bound it

Timing

Cadence & freshness

  • Observe and lead status check on the heartbeat schedule (default 1 h weekday working hours, 2 h otherwise)
  • Evidence valid ≤ 30 min · prepare metadata ≤ 5 min
  • Paused > 30 days → one reminder

Per wake (lead turn)

Allowance

  • 5 PR visits · 40 provider requests · 120 s
  • takeDue reserves ADO 39 · GitHub 8 · recovery 1
  • Recovery: 3 alternate attempts / incident, 20-incident history

Per authorization

Budgets & brakes

  • 3 repair batches · 3 answer batches · 100 mutation attempts
  • 1 outstanding batch · 1 retained PR per task
  • Auto-pause: 3 consecutive / 10 total failures · 3 stalls · 2 no-progress

Preparation is repair-only. There is no observation-only mode: PreparePrMaintenanceSchema.mode is the literal "repair", PrMaintenanceScopeSchema requires publicationAuthorized: true, and a missing publicationEvidence is refused with publication_evidence_required before any proposal exists. Replies, thread resolution, named reviewers and CI retries default off. Legacy observation-only grants stay readable but authorize nothing; they show as authorization_required until a new repair proposal is authorized.
