# Reusable chat-history benchmarks

Run these before and after changing history loading, event merging, transcript
folding, or permission/preview processing:

```powershell
npm run benchmark:history -- --output dist\benchmarks\before.json
npm run benchmark:history -- --baseline dist\benchmarks\before.json --output dist\benchmarks\after.json
```

The runner uses the existing `tsx`, SQLite, Fastify, and application dependencies.
Run `npm ci` on a fresh checkout first. No additional browser or benchmark package
is needed. Results go under the already-ignored `dist` directory by default; save
named reports when comparing commits because the default report is overwritten.

## Workload and reproducibility

The default fixture has **112,000 lead events**, **25 background sessions with
8,000 events each**, and **5,600 lead blocks**. It models the reported shape of
long conversations, not anyone's actual chat content: each 200-event turn has
170 short text/thought chunks, repeated command/config/usage payloads, permissions,
interleaved tool updates, and ten rendered blocks. There are folded control
messages, Markdown tables/code, non-ASCII text, and a large tool response.

All content and event ordering are deterministic. Session IDs are generated by
the real store and are not exported in the report. The fixture is versioned;
change its version when changing the workload so reports do not silently compare
different inputs.

Each operation gets **5 warm-up iterations and 30 measured iterations**. JSON
reports retain every sample, nearest-rank median/P95, min/max, fixture counts and
event-type mix, Node/OS/CPU information, Git revision, and whether the checkout
was dirty. GC is not forced, so allocation/GC costs remain part of the workload.

Use the same machine, Node version, options, and background load for comparisons.
The comparison command rejects incompatible fixtures, environment identifiers,
and warm-up/sample counts. It prints P95 changes without enforcing timing gates:
positive percentages mean slower. Shared developer machines are too noisy for
absolute latency assertions in the normal test suite.

## Options

| Option | Default | Meaning |
|---|---|---|
| `--events` | `112000` | Lead-session raw event count, from 200 to 2,000,000 |
| `--sessions` | `26` | Total cached sessions; each background history has `ceil(events / 14)` events |
| `--iterations` | `30` | Measured repetitions per stage and HTTP scenario |
| `--warmup` | `5` | Unreported repetitions before measurement |
| `--output` | `dist/benchmarks/history.json` | JSON report destination |
| `--baseline` | None | Earlier compatible JSON report for P95 comparison |
| `--help` | | Show usage |

A quick functional smoke run, not a reliable performance baseline:

```powershell
npm run benchmark:history -- --events 400 --sessions 2 --iterations 3 --warmup 1 --output dist\benchmarks\smoke.json
```

For a smaller performance workload, use `--events 11200`; for a 10x stress workload,
use `--events 1120000`. The stress run loads all configured histories plus temporary
parse/fold representations and can use substantial memory. Run it deliberately,
not in parallel with builds or the representative workload.

## What the numbers measure

| Measurement | Scope |
|---|---|
| `diagnostic.sqlSelect` | Prepared SQLite `SELECT` on the synthetic event table |
| `diagnostic.decodePayloads` | Row conversion and payload `JSON.parse` |
| `diagnostic.validateOuterSchema` | `SessionEventSchema.parse` over decoded rows |
| `store.listEvents` | The production store reader, including its current decoding/validation |
| `store.listTranscript` | The production filtered browser-history reader, including activity metadata |
| `diagnostic.readThenFilter` / `store.listEventsAfter` | Legacy full read then filter / indexed read of the last 10% of events; results must match |
| `history.stringify` / `history.parse.node` | Serializing the current browser-history response and parsing it in **Node** |
| `transcript.fold` | The existing `toTerminalBlocks` implementation |
| `events.merge.*` | Existing `mergeEvents` for explicit text, thought, older-tool, and permission events |
| `transcript.update.*` | Merge **plus** full folding, matching the current UI's data path |
| `permissions.allCached` | Legacy all-session flatten-and-scan diagnostic |
| `store.listPermissionEvents` / `permissions.liveText` | Compact permission hydration / current index handling of a text update |
| `preview.last12` | Current preview generation, including any work before taking the last 12 lines |
| `http.history.ttfb` / `http.history.total` | Headers received / complete body consumed from the real session history route |
| `http.probe.idle` / `http.probe.duringHistory` | A lightweight request without / with a concurrent history request |
| `hostEventLoop` | Event-loop-delay mean, P95, and maximum in the server process, at 10 ms sampling resolution |

The HTTP client runs in the parent process. The production browser transcript route runs
in a separate child on an ephemeral `127.0.0.1` port, using a disposable SQLite
database. A separate keep-alive connection probes responsiveness when an IPC
signal announces the start of history handling. This avoids confusing a blocked
client event loop or connection-pool queue with a blocked Host.

HTTP includes normal history-route work, including its activity touch, but not
production authentication, TLS, compression, reverse proxies, Node gateways,
or live agents. The event-loop histogram also includes idle/probe intervals;
inspect its **maximum**, not only its percentile. Do not add independently timed
stages together and label the result end-to-end latency. In particular,
`transcript.update.*` already includes merging.

Sizes are **UTF-8 bytes**, not JavaScript string lengths. The report includes the
real HTTP body size, raw canonical history size, and estimates for filtering bookkeeping events, serializing
all blocks, and serializing the last 200 blocks. Block estimates do not measure block-page production cost. Reports from the original
baseline used the raw `/events` route; the current runner follows the UI's filtered
`/transcript` route. That is an intentional before/after comparison of the history
the browser actually downloads, not a claim that the canonical event log shrank.

## Safety and maintenance

The harness never opens the live Host database, connects to an existing Host,
starts agents, or sends prompts. It creates its own temporary database, seeds
validated synthetic events outside the timed section, and cleans it up on normal
completion/failure. The isolated server refuses routes other than the measured
GET and its ping. Forced process termination can leave a named
`fleet-history-benchmark-*` temporary directory.

The benchmark stays separate from `npm test` and `npm run verify`. A tiny harness
smoke test and deterministic correctness checks run in the existing suite;
benchmark code is also included in `npm run typecheck`.

Production imports live in `scripts/benchmarks/history.ts`. Keep these calls tied
to the actual implementation when introducing incremental processing or block
paging; do not leave a copied legacy algorithm masquerading as a measurement of
the new path. The `diagnostic.*` stages are explicitly diagnostic reproductions.
Update response correctness expectations when the history API intentionally
changes, while preserving metric names for workloads that remain comparable.

This harness does **not** measure React rendering, layout, paint, scrolling, or
typing latency. Use the same versioned fixture for the separate production-browser
performance harness in the chat optimization plan. Node-stage improvements alone
do not establish that the UI's latency targets have been reached.
